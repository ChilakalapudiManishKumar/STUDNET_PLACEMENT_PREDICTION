# Student Placement Prediction Using Machine Learning

This is an end-to-end data science project where I built a model that predicts whether a student is likely to get placed during campus recruitment, based on things like CGPA, coding score, internships, and communication skills. It's not just a model though — it also comes with a small web app where you can type in a student's details and instantly see a prediction.

I built this as a learning project to go through the *entire* data science lifecycle properly, from messy raw data all the way to a deployed web app, instead of just training a model on an already-clean dataset (which is honestly what most tutorials do, and it skips the hardest part of real data science).

---

## Why this project exists

Every "placement prediction" dataset I could find online was already clean — no missing values, no typos, no duplicate rows. That's not what real data looks like. In an actual college, placement records get typed in by different staff across different years, so you end up with things like "Excellent" spelled three different ways, a CGPA of 13.2 typed in by mistake, or the same student appearing twice.

So instead of downloading a dataset, I generated my own — synthetically, but with all of that mess baked in on purpose. That way the cleaning and preprocessing steps in this project are actually solving real problems, not just going through the motions.

## The dataset

1,000 synthetic student records (plus some intentional duplicates, so the raw file has slightly more rows than that) with these columns:

- **Student_ID** — unique identifier (with ~15 intentionally repeated IDs)
- **CGPA** — mostly 6.0–9.8, but with some garbage values thrown in (negative numbers, values above 10, text like "Nine")
- **10th_Percentage / 12th_Percentage** — academic percentages, again with some invalid entries
- **Internships** — number of internships completed (0–4)
- **Coding_Score / Aptitude_Score** — test scores out of 100
- **Communication** — Poor / Average / Good / Excellent, but typed inconsistently (GOOD, good, GoOd, Exellent, Avarage, etc.)
- **Projects** — number of academic/personal projects
- **Backlogs** — number of active backlogs
- **Placement** — the target column: whether the student got placed, again written inconsistently (Yes, YES, Y, Placed, Selected all mean the same thing)

Placement outcomes aren't random — students with higher CGPA, better scores, more internships, and fewer backlogs are more likely to be placed, but I deliberately added some borderline cases (a strong student who didn't get placed, a mediocre one who did) because that's how real placement outcomes actually look. Nothing in real life is 100% predictable from a spreadsheet.

## How I approached it, step by step

### 1. Loading and first look at the data
Before touching anything, I just looked at the data — `head()`, `shape`, `info()`, `describe()`. This alone told me a lot: seven of the eleven columns were loading as text instead of numbers, which is a dead giveaway that the column contains a mix of numbers and stray text values.

### 2. Figuring out what was actually wrong
I checked for missing values, duplicate rows, duplicate IDs, and how many different spellings existed in the text columns. This step is really just about understanding the size of the problem before trying to fix it — you can't clean what you haven't measured.

### 3. Cleaning
This was the biggest chunk of work. In order:
- Removed exact duplicate rows first
- Removed rows with repeated Student_IDs (kept the first one — no reliable way to know which duplicate was "correct")
- Wrote a function to turn messy numeric entries into real numbers — stripping `%` signs, fixing comma-decimals like `8,5`, and converting spelled-out numbers like "Eighty Five" into 85
- Nulled out anything outside a sensible range (like a CGPA of 13.4 or a Coding Score of 150) rather than keeping obviously wrong values
- Standardized the Communication and Placement columns into a strict, consistent set of categories
- Dropped rows where the placement outcome itself was unrecoverable — you can't train on a label you don't actually know
- Filled remaining missing numeric values with the column median (safer than the mean since a few outliers can drag the mean around) and missing Communication values with the most common category
- Capped outliers using the IQR method instead of deleting them, so I didn't lose more data than necessary

After all this, I went from 1,020 raw rows down to 936 clean, trustworthy ones.

### 4. Exploring the clean data
Once the data was trustworthy, I made a batch of charts — histograms, box plots, a correlation heatmap, scatter plots, a pair plot, and some bar charts comparing placement rate across categories. The clearest patterns: placed students had noticeably higher CGPA, coding scores, and internships, and noticeably fewer backlogs. Communication mattered too — placement rate climbed steadily from Poor to Excellent.

### 5. Creating new features
Rather than just feeding the raw columns into a model, I built three combined features:
- **Academic_Score** — blends CGPA and both board percentages into one number
- **Experience_Score** — internships (weighted more heavily) plus projects
- **Skill_Index** — average of coding and aptitude scores, minus a penalty for backlogs

These ended up being the two most important features in the final model, which was a nice confirmation that combining related signals gave the model something better to work with than the raw numbers alone.

### 6. Encoding
Communication got label-encoded (Poor=0, Average=1, Good=2, Excellent=3) instead of one-hot encoded, because there's a genuine order to those categories — one-hot encoding would have thrown that ordering away for no benefit.

### 7. Scaling
Used StandardScaler so that every feature is on the same scale before training. Without this, a feature like Skill_Index (which can go up to 100) would end up dominating a feature like CGPA (which tops out at 10) purely because of the size of the numbers, not because it's actually more important.

### 8. Splitting into train and test sets
80/20 split, stratified so both sets kept the same ~60/40 placed/not-placed ratio as the full dataset. Without stratifying, you can accidentally end up with a test set that's, say, 90% "placed" by pure chance, which would make your accuracy numbers meaningless.

### 9-10. Training and evaluating models
Trained six models — Logistic Regression, Decision Tree, Random Forest, SVM, KNN, and XGBoost — and compared them on accuracy, precision, recall, F1, and ROC-AUC. Logistic Regression came out on top overall (best F1), SVM had the best precision and accuracy, and KNN was the weakest performer. None of them broke into the 90s, and that's expected — the dataset has real, deliberate noise in it, the same way actual placement outcomes do. A model that hit 95%+ accuracy on data like this would actually be a red flag for overfitting, not a win.

### 11. Feature importance
Using the Random Forest's built-in importance scores, Skill_Index and Academic_Score — the two features I engineered — came out as the most influential, ahead of any single raw column. That's exactly the outcome you want from feature engineering: showing that combining related signals gives the model more to work with than the individual pieces.

### 12. Saving the model
Saved the best model and the scaler using Joblib, so they can be loaded instantly for predictions without retraining from scratch every time.

### 13. Building the web app
Wrapped everything into a Streamlit app where you fill in a student's details and hit Predict. It shows the prediction (Placed / Not Placed), the raw probability, and a confidence score — the confidence score matters because a low probability of placement is really just a high-confidence "Not Placed" prediction, and I wanted that to be clear rather than confusing.

## Running it locally

Everything needs to sit in one folder together, and the scripts have to run in this order the first time, since each one depends on the previous one's output:

```bash
pip install -r requirements.txt

python pipeline.py            # cleans the raw data
python eda.py                  # generates the charts in /plots
python prep_model_data.py      # feature engineering + train/test split
python train_models.py         # trains and compares all models, saves the best one

streamlit run app.py           # launches the web app
```

Once `best_model.joblib` and `scaler.joblib` exist, you can also just run `predict.py` to test a single student from the terminal without opening the web app at all.

---

## Deploying to Streamlit Community Cloud

1. Push the whole folder to a GitHub repository — code, `requirements.txt`, and both `.joblib` files all need to be in there.
2. On [share.streamlit.io](https://share.streamlit.io), connect the repo and point it to `app.py`.
3. Make sure `requirements.txt` sits either in the repo root or in the same folder as `app.py` — Streamlit Cloud won't install anything beyond Streamlit itself if it can't find this file, which is the single most common deployment error.
4. Deploy, and Streamlit Cloud handles the rest.

A couple of things I ran into while deploying that are worth knowing about upfront:
- If the model was trained with a different scikit-learn version than what's installed where you're running it, you can get strange attribute errors on load. Pinning versions in `requirements.txt` (or just retraining locally with the same versions listed there) avoids this.
- Folder names don't matter — the scripts figure out file paths relative to their own location, so you can rename the project folder freely as long as everything inside it stays together.

## Results summary

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|
| Logistic Regression | 0.654 | 0.709 | 0.728 | 0.719 | 0.710 |
| XGBoost | 0.660 | 0.745 | 0.667 | 0.704 | 0.700 |
| SVM | 0.676 | 0.805 | 0.614 | 0.697 | 0.689 |
| Decision Tree | 0.654 | 0.748 | 0.649 | 0.695 | 0.690 |
| Random Forest | 0.660 | 0.772 | 0.623 | 0.689 | 0.709 |
| KNN | 0.601 | 0.682 | 0.640 | 0.661 | 0.655 |

For context, a model that just guessed the majority class every time would land around 60.5% accuracy, so every model here is genuinely learning something from the data rather than just exploiting the class imbalance.

## What I'd add if I kept going

- Hyperparameter tuning (GridSearchCV) to squeeze a bit more performance out of the top models
- Cross-validation instead of a single train/test split, for a more reliable performance estimate
- A batch-prediction option in the app — upload a CSV of many students at once instead of one at a time
- More realistic features if this were ever used on real data — things like specific technical skills or mock interview scores would likely carry more signal than what's available here

## A note on the dataset

This dataset is synthetic — I generated it myself to have realistic messiness to clean, and the placement outcomes follow a designed pattern (with some intentional noise) rather than reflecting any real institution's actual data.
